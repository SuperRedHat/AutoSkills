# 在会话里起长跑驱动：部署前的三次真实探查（AS3-373）

2026-11-20，在一次性测试仓库上做。看三件事：会话起的驱动能不能活过起它的会话；照新文字做的会话会不会把事情做对；驱动还在跑的时候，另一个说“继续”的会话是不是只读。

做了三次。每次之后独立校验都让文字改了，所以用改后的文字重做（见“每次之后改了什么”）。现在仓库里的文字就是第三次用的；第三次还在起驱动之前放了一把旧锁。

## 结论

三次的结果一样：

- 一个真实会话听到“起长跑，只做 N 个任务，模型用 claude-opus-5-5，档位 high”，照新文字在新窗口里起了驱动，选项是 `--max-tasks N --model claude-opus-5-5 --effort high`。它起之前在账本里记了一条，起之后没有再写账本。
- 起它的会话结束以后，驱动接着跑，做完 N 个任务后以“到了 --max-tasks”停下，退出码 0。每个任务的复验都通过。
- 驱动还在跑的时候，第二个真实会话说“继续”：它查到锁，核对出驱动还活着，只读汇报，没有写账本，没有改文件。
- 账本文件的每一次变化都落在某个会话之内（三次分别是 14、7、7 次）。落在第二个会话那段时间里的，是驱动的会话在改任务状态。
- 自动模式没有拦起窗口的命令，所有会话的权限拒绝都是 0 次。

第三次多出来的一条：

- 起之前项目里有一把旧锁（锁里的进程已经不在了）。会话核对出 `driver alive False`，没有删它，照常起；驱动自己接手了这把锁，报告里记了一句；会话等到锁的内容变了，再核对是 `driver alive True`，报给用户的是新的运行名。

三次一共用掉 511 万 token，按命令行报的美元是 4.52 美元。

## 起驱动的会话做了什么

三次的顺序一样：

1. 读了新文字的两个文件（project-next 的“长跑”一节和 `long-run.md`）。
2. 设项目目录，看了 `git status`（干净）、项目契约和账本里的任务（有就绪的），看了有没有驱动在跑。第三次这里用页面上的那段核对了旧锁，结果是 `driver alive False`，没有删它。
3. 跑了那段找脚本的 PowerShell，找到主检出的 `scripts/autoskills.mjs`。
4. 用 `add_log` 记了一条：要起长跑、选项、当时的时间。这是它唯一一次写账本，比驱动开始早 6 到 8 秒（三次分别是 7.7、7.3、6.2 秒）。
5. 起了新窗口，核对锁。第三次用的是现在页面上的两段：起并等锁的那一段输出 `new lock`，核对的那一段输出 `driver alive True`。前两次用的是当时的写法（等几秒读锁，再查进程）。
6. 告诉用户运行名、选项、报告的位置、怎么停、不要直接关窗口，然后结束。第三次还说了起之前有一把旧锁、驱动接手了它。

文字没有要求、它多做的事（都只读）：看了一下主检出的驱动脚本认哪些选项；前两次还跑了一次 `help run`。

## 说“继续”的会话做了什么

1. 读了新版 project-resume。
2. 和读 git 的命令一起看了锁文件。后两次接着读了 `long-run.md`，跑了核对的那一段，结果是 `driver alive True`；第一次是自己用 `Get-Process` 查的。
3. 调的账本工具都是读（设项目目录、读服务信息、读项目上下文或任务列表）。没有调写账本的工具，没有用写文件的工具。
4. 告诉用户长跑在跑（运行名、开始时间），以及等它跑完、让它停、只看进度这几种做法。

## 每次之后改了什么

**第一次之后。** 独立校验第 1 轮判不通过，唯一的一条大问题是缺一份日志（新文档带私有词表的 lint 跑过但没留日志，补了）；行为上没有发现问题，另提了 8 条小问题，都改了：

- 等锁从“等 5 秒读一次”改成最多等 20 秒。
- 查锁改成一段 PowerShell 直接给出结论。进程要活着、是 node、启动得不比锁里记的开始时间晚，才算驱动；原来不比启动时间，进程号被别的进程用上时会判错。
- 读设置文件和钩子配置时按 UTF-8 读。原来不指定，文件里有中文时 Windows PowerShell 5.1 会读坏。
- project-resume：没有锁文件就不用去读那一页；读驱动报告的条件改成“报告比账本最后一条日志新”；运行目录里没有报告的，按驱动被强行结束处理。

**第二次之后。** 独立校验第 2 轮判不通过，问题是上一轮的修改引进的：起驱动之前项目里已经有一把旧锁时，等锁的那一段会立刻读到旧锁，报出旧的运行名；而且“旧锁不用删”和驱动的实际行为对不上（锁里的进程号被别的进程用上时，驱动只看那个号还在不在，会拒绝起）。先试的改法是“核对出驱动不在就删锁”，专门挑错的一遍读指出它有两条路会删掉活驱动的锁，所以这一页重排了：

- “核对锁”单独成一节。多了一个结果 `driver alive Unknown`：锁读不清、进程查不了，都算它，并且当成驱动在跑。
- 会话不再自己删锁。只有一种情况会删：起驱动时锁没有变、核对是 `driver alive False`、用户说删、再核对一次还是 `False`。
- 起驱动改成一段一次执行的 PowerShell：记下起之前锁的内容，起窗口，等锁的内容变，输出 `new lock`、`no lock` 或 `the lock did not change`。
- 起窗口时不再指定工作目录：PowerShell 把它当通配符，项目目录名里有方括号时起不来（新加的测试查出来的）；驱动的项目目录本来就是从参数取的。路径一律按字面读。
- project-resume 里给驱动自己起的会话留的例外挪到了最前面。project-feedback 改成用同一段核对。“停下长跑”先核对锁。

project-next 的 `SKILL.md` 三次之间没有改。

## 没有探到的

- **自然触发。** 只说一句“起长跑”、不指文件时，部署后的技能会不会被用上，这三次探不了，放在 AS3-375。
- **驱动自己起的会话读到新文字会怎样。** 三次里驱动的会话读的都是用户级的旧技能。新文字给它们留的例外，是按提示词里“这是无人值守的运行”这句话认的；测试只钉住了这句话在两边的字面一致和例外写在查锁之前，没有真实会话验过。放在 AS3-375。
- **开着窗口的交互式会话。** 这三次的会话都是无头的。
- **驱动停了以后说“继续”。** 新版 project-resume 这时要读一遍驱动的报告，并记一条日志。没有跑：会话会接着把剩下的任务做完。
- **锁的几种少见情况。** 锁里的进程号被别的进程用上（驱动拒绝起，结果是 `the lock did not change`）、锁读不清（`Unknown`）、用户说删以后的删锁，这些只在测试里用替身进程验过，没有真实会话碰到。
- **project-feedback 的新查法。** 没有真实会话走过；它和 project-resume 用的是同一段核对。
- **“停下长跑”和 Ctrl+C。** 主控替负责人跑 `stop` 这一句没有跑，`stop` 命令自己有测试。在驱动的窗口里按 Ctrl+C、直接关掉那个窗口，都没有试。
- **PowerShell 7。** 这台机器只有 Windows PowerShell 5.1，核对锁的那一段没有在 PowerShell 7 上跑过。
- **一个环境因素。** 测试仓库在 AutoSkills 仓库里面，会话读得到 AutoSkills 自己的契约，其中有一句“长跑驱动在本仓库上跑着的时候，别的会话不记账”。说“继续”的会话确实照新文字查了锁，但不能排除这句话也起了作用。负责人别的项目里没有这句话。

# /project-quick — 小事快修

快修只是省掉规划，不省掉证据：照样验证、照样提交、照样记录。证据和提交规则以自主契约为准。三个前提由代理自己判断，不停下来问用户；拿不准就当作不满足，转成正式任务。

## 1. 能不能用
- 本会话还没调过时，用主检出的绝对路径调 `set_project_dir`，再用 `get_server_info` 核对 state_files；读项目契约（仓库根目录的 AGENTS.md）里的只读目录、默认验证命令和重型套件。
- 用 `get_all_tasks(status="in_progress")` 和 `get_all_tasks(status="auto_verified")` 看有没有进行中的任务；本会话正在跑 project-next 的循环或 /goal 也算进行中。
- 有进行中的任务或循环时不快修：用 `create_tasks` 把这件事记成任务（字段按 project-plan 第 3 步，notes 写用户原话），交给循环处理；不在本轮范围内的，在 notes 写"本轮范围外，待用户安排"，不擅自扩大范围。
- 没有账本时照样可以快修，第 4 步的记录写进提交说明，并在汇报里写"未入账本"。

## 2. 三个前提（同时满足）
1. 不碰门禁和接口：
   - 门禁：测试、基线、验证命令和验证配置，CI、钩子和守卫规则，账本里的验收字段，stage_gate 和本人验收点。
   - 接口：别的模块或别的项目在用的函数签名、API、命令行参数、数据格式、文件格式和配置键。
   - 也不碰：只读目录、用户级文件（`~/.claude`、`~/.codex` 下的文件等）、安全和权限相关的代码、视觉基线。
2. 一次提交就能回滚：改动放在一个提交里，`git revert` 这一个提交就能完全恢复；没有数据迁移、删除数据、改外部状态或其他不可逆的副作用。
3. 不需要重型套件：项目契约默认验证命令里的轻量检查（加上和改动直接相关的测试）就足以证明改对了；需要项目契约列出的重型套件、端到端或浏览器测试、长时间运行或人看外观的，不满足。

## 3. 转成正式任务
- 开始前有一条不满足，或做到一半发现不满足（如要改接口、要动测试才能过），就停止快修：用 `create_tasks` 建正式任务，字段按 project-plan 第 3 步（风险等级、验收模式、verification_commands、review_checklist 都要写），notes 写明是从快修转来的、哪条前提不满足、已经改了什么。
- 已改的东西留在工作区，不丢弃，交给这个任务继续用。
- 用户本轮已经要求修这件事的，建完任务直接进入 project-next 的循环做它；会改已确认的项目级设计的，转 project-plan 第 5 步。

## 4. 修、验证、提交、记录
- 改动只限这件事本身；顺手发现的别的问题记下来，不一起改。
- 在仓库根目录跑项目契约里的默认验证命令和相关测试，打印命令、退出码和日志位置；失败就修，修不好就按第 3 步转正式任务。
- 提交：Conventional Commits，说明里写 `quick`，如 `fix(ui): correct label typo (quick)`；只 `git add` 改动的文件，不用 -A，不用 `.`，也不用 -f。提交号用 `git rev-parse HEAD` 读出。
- `add_log` 记一条：type 写 "quick_fix"，kind 写 "note"；message 写改了什么、为什么、三个前提各自怎么判断的、验证命令和退出码、提交号；entities 写成对象，如 `{"commit": "<提交号>", "files": ["src/ui/label.ts"]}`。
- 汇报：改了什么、命令和退出码、提交号；转成正式任务的，写任务 id 和原因。
